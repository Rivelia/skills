# Reporting a simplify.mjs result

When the result carries `skipped`, the workflow never started simplifying: say so, with `skipped` (`nothing-to-simplify` when no source file was left in scope after the exclusions, `prepare-failed` when the file lists could not be read, `comments-failed` when the opening comment pass threw, its commit agent committed without reporting a valid HEAD sha, or its commit agent died or did not report a clean tree, which you state prominently because its edits may sit uncommitted in the working tree) and `error`, and report nothing else, except that for `comments-failed` with a non-null `comments.opening` you also report it by `WORKFLOW-REPORT.md` in the `no-comments` skill folder as a pass whose simplify did not run, so its seeds are listed as left for the user.

When `comments.opening` is present, report it first by `WORKFLOW-REPORT.md` in the `no-comments` skill folder: the comments stripped before the loop, and the seeds it handed to the judge.

Then the seed stage, from `seeds`: `proposed`, `approved`, and each entry of `applied` with its `kind` (`must-kill` or `constraint`), its symbol and what changed; for a constraint, its `seed` (the constraint) and `enforcedBy` (the kind of enforcement and where it lives), prominently, saying the user should check each encoding was done properly, and naming a `runtime-check` as one that changes behaviour. List `rejected` with the judge's reason and `failed` with why, each with its `description`; each rejected or failed `constraint` is a constraint whose comment was deleted with nothing enforcing it, so say so prominently, with its file and its `description` (the constraint).

Relay `summary` grouped under its two headings (`Performance improvements`, `Code simplifications`), plus the round count (`iterations`), the sweep count (`sweeps`), and the proposed/approved/applied counts (`findingsProposed`, `findingsApproved`, `changesApplied`); the gap between proposed and approved is the judge doing its job. Relay every entry in `rejectedFindings` under its own heading, with its description (its first sentence), its files, and the judge's reason, so the user sees what the judges struck and why; when `rejectedTotal` is larger, say how many more they struck.

State the commit from `commit`: its sha and files, or its `reason` when nothing was committed; name any `discarded` check outputs, deleted instead of committed. When `comments.closing` is present, report it by the same `WORKFLOW-REPORT.md`: its `mustKills.reported` are refactors the appliers' comments excused, left for the user.

Then state every entry of `reportLines`, in order, the ones marked `prominent` prominently. They are the run's caveats, computed from fields the result does not carry: drop none, soften none, and add none of your own. In particular, make no claim the lines contradict: that the scope converged, that comments were fully audited, or that the project passes its check.

When `unresolvedCheckFailures` is non-empty, first fix any breakage yourself in files the workflow touched, and commit the repair; then list what still remains, prominently, saying the workflow's own fix-up agent already tried and failed to repair these. An entry whose `file` is null names no path, because the fix-up reported the check still failing without naming any failure; treat it as a failure with no known location and open no file for it.

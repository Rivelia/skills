# Reporting a simplify.mjs result

When the result carries `skipped`, the workflow never started simplifying: say so, with `skipped` (`nothing-to-simplify` when no source file was left in scope after the exclusions, `prepare-failed` when the file lists could not be read) and `error`, and report nothing else.

Relay `summary` grouped under its three headings (`Performance improvements`, `Code simplifications`, `Bug fixes`), plus the round count (`iterations`), the sweep count (`sweeps`), and the proposed/approved/applied counts (`findingsProposed`, `findingsApproved`, `changesApplied`); the gap between proposed and approved is the judge doing its job. Relay every entry in `rejectedFindings` under its own heading, with its description (its first sentence), its files, and the judge's reason, so the user sees what the judges struck and why; when `rejectedTotal` is larger, say how many more they struck. When `prune` carries `removed`, report it with `batchesDone`/`batchesTotal` and `iterations`.

Then state every entry of `reportLines`, in order, the ones marked `prominent` prominently. They are the run's caveats, computed from fields the result does not carry: drop none, soften none, and add none of your own. In particular, make no claim the lines contradict: that the scope converged, that comments were fully audited, or that the project passes its check.

When `unresolvedCheckFailures` is non-empty, first fix any breakage yourself in files the workflow touched; then list what still remains, prominently, saying the workflow's own fix-up agent already tried and failed to repair these. An entry whose `file` is `(unattributed)` names no path, because the fix-up reported the check still failing without naming any failure; treat it as a failure with no known location and open no file for it.
